# Deployment Runbook

This project has three runtime pieces:

- Dashboard: Next.js app.
- Backend API: Express app for REST, Socket.IO, uploads, and Meta webhook ingestion.
- Worker: BullMQ process for webhook jobs and maintenance jobs.

## Render + Vercel deployment (this project's setup)

`render.yaml` at the repo root is a Render Blueprint that provisions the backend
as a **single web service** that also runs the BullMQ worker in-process
(`START_EMBEDDED_WORKERS=true`), backed by a **persistent disk** for uploaded media.
The dashboard is deployed separately on **Vercel**. PostgreSQL and Redis are existing
managed instances whose URLs you paste into the service.

Why single-service: a Render disk can only attach to one service and pins it to one
instance. Running the API and worker together on that service keeps product images and
WhatsApp media on the disk without an object store. This is the right trade-off for a
single boutique. To scale out later, move media to S3/Cloudinary (the `StorageService`
interface in `apps/backend/src/storage` is the seam) and split the worker into its own
service with `START_EMBEDDED_WORKERS=false`.

### Backend on Render

1. Push this repo to GitHub.
2. In Render: **New → Blueprint**, point it at the repo. It reads `render.yaml`.
3. Fill the `sync: false` env vars in the Render dashboard:
   - `DATABASE_URL` — your managed Postgres URL (`?sslmode=require` recommended).
   - `REDIS_URL` — your managed Redis URL. Use the `rediss://` (TLS) form; BullMQ TLS
     is enabled automatically for `rediss://`.
   - `PUBLIC_BACKEND_URL` — this service's URL, e.g. `https://kda-backend.onrender.com`.
   - `PUBLIC_DASHBOARD_URL` — the Vercel dashboard URL (drives CORS + cookie checks).
   - Meta credentials, `GEMINI_API_KEY`, `UPI_ID`, `OWNER_WHATSAPP_NUMBER`, etc.
   - Leave `SESSION_COOKIE_DOMAIN` blank for the Vercel + Render setup.
   - `SESSION_SECRET` is auto-generated by the blueprint.
4. The blueprint runs `db:migrate:deploy` as a pre-deploy step on every release and
   starts the API with `npm run start:backend`. The service binds to Render's `PORT`
   automatically.
5. After the first successful deploy, seed the admin once from the service **Shell**:
   ```bash
   SEED_ADMIN_EMAIL="you@example.com" SEED_ADMIN_PASSWORD="<strong>" npm run db:seed
   ```
6. Health check is `GET /health` (already wired in the blueprint).

### Dashboard on Vercel

1. Import the repo into Vercel.
2. Set **Root Directory** to `apps/dashboard` (it auto-detects the npm workspace).
3. Set env var `NEXT_PUBLIC_BACKEND_URL=https://kda-backend.onrender.com` (your Render URL).
4. Deploy. Vercel runs `next build`.

### Cookies across Render + Vercel

Browser REST calls use same-origin dashboard paths (`/api/*`). Vercel rewrites those
requests to Render, so Safari stores the `kda.sid` cookie as a first-party dashboard
cookie instead of a third-party Render cookie. Keep `SESSION_COOKIE_DOMAIN` blank for
this setup. `SESSION_COOKIE_SAMESITE=none` is still safe for direct API calls and for
future custom-domain layouts.

The sections below describe the generic/manual deployment flow (e.g. a separate worker
service) and remain valid if you choose a different topology.

## Required Services

- Node.js 20+
- PostgreSQL database
- Redis instance
- Persistent media storage
  - Current implementation uses local filesystem uploads under `uploads/`.
  - For a real production host, use persistent disk or migrate storage to S3, Cloudinary, or Supabase Storage before relying on uploaded product/payment media.

## Database

Run migrations before starting the app:

```bash
npm run db:migrate:deploy
npm run db:generate
```

Create the first production admin only after setting `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD`:

```bash
SEED_ADMIN_EMAIL="admin@example.com" SEED_ADMIN_PASSWORD="strong-password-here" npm run db:seed
```

## Backend API Process

Required command:

```bash
NODE_ENV=production npm run start:backend
```

The backend exposes:

- `GET /health`
- `GET /webhook/whatsapp`
- `POST /webhook/whatsapp`
- `/api/*`

In production, embedded workers are disabled by default. Keep `START_EMBEDDED_WORKERS=false` and run the worker command below as a separate service.

## Worker Process

Required command:

```bash
NODE_ENV=production npm run start:worker
```

The worker connects to Postgres and Redis on startup, starts the WhatsApp webhook queue worker, and schedules maintenance jobs for expired reservations and stale conversation cleanup.

Printing notes:

- `PRINT_PROVIDER=manual` generates a PDF and returns the PDF URL from print routes. This is safe for demos and for deployments without printer credentials.
- `PRINT_PROVIDER=printnode` sends the generated PDF to PrintNode when `PRINTNODE_API_KEY` and the matching printer ID are configured. PDF generation remains the fallback if PrintNode is unavailable.
- `AUTO_PRINT_ORDER_LABELS=true` creates one idempotent `ORDER_LABEL` print job after owner payment approval. The on-site Windows bridge claims and prints it.
- `PRINT_AGENT_TOKEN` is backend-only and bridge-only. Never expose it to Vercel/browser JavaScript.

## Windows Label Print Bridge

Install and run this on the shop laptop connected to `4BARCODE 4B-2054TG`.

Bridge `.env`:

```bash
BACKEND_URL=https://your-backend.example.com
PRINT_AGENT_TOKEN=<same secret as Render>
DEVICE_ID=kanika-shop-laptop-01
PRINTER_NAME=4BARCODE 4B-2054TG
POLL_INTERVAL_MS=3000
HEARTBEAT_INTERVAL_MS=30000
PRINT_JOB_BATCH_SIZE=1
LABEL_SIZE=4x3
PRINT_DRY_RUN=true
OUTPUT_DIR=./print-output
```

Commands:

```bash
npm install
npx playwright install chromium
npm run printers:list
npm run printer:diagnose
npm run bridge:dry-run -- --template=manual-receipt
npm run bridge:dry-run -- --template=online-order-label
npm run print:test -- --template=manual-receipt
npm run print:test -- --template=online-order-label
npm run bridge:start
```

For the first physical test, keep `PRINT_DRY_RUN=true` and confirm the HTML/PDF in `apps/print-bridge/print-output`. Then set `PRINT_DRY_RUN=false`, keep the Windows driver on the manually tested 4x3 stock, and run both `print:test` commands above. The bridge does not pass orientation, scaling, fitting, paper-size, or rotation options to Windows.

Current 4x3 HTML renderer:

- PDF physical page: `101.6 mm x 76.2 mm`
- HTML/CSS source: tested full-page label CSS
- PDF rotation metadata: `0`
- Windows print call: `{ printer: PRINTER_NAME }`

Cookie notes:

- Current Vercel + Render setup: `SESSION_COOKIE_SAMESITE=none`, `SESSION_COOKIE_SECURE=true`, and `SESSION_COOKIE_DOMAIN` blank.
- Future shared custom domain: use `SESSION_COOKIE_SAMESITE=lax`; set `SESSION_COOKIE_DOMAIN=.kanikaboutique.com` only if you need the cookie shared across subdomains.
- The browser cookie contains only a signed `kda.sid` session identifier; session data lives in Redis and is mirrored to Postgres.

## Meta Webhook Setup

Callback URL:

```text
https://your-backend.example.com/webhook/whatsapp
```

Verify token:

```text
META_WEBHOOK_VERIFY_TOKEN
```

Subscribe to:

- `messages`
- `smb_message_echoes`
- `smb_app_state_sync`
- `history`

The webhook verifies `x-hub-signature-256`, enqueues the payload, and returns `200` before job processing.

## Smoke Test Checklist

1. Run `npm run db:migrate:deploy`.
2. Run `npm run db:generate`.
3. Seed admin with `SEED_ADMIN_PASSWORD`.
4. Start backend API.
5. Start worker.
6. Open `https://your-backend.example.com/health`; confirm DB is `up` and Redis is `up`.
7. Open dashboard URL.
8. Log in with seeded admin.
9. Upload a test product image and confirm it appears in inventory.
10. In Meta dashboard, verify webhook with `https://your-backend.example.com/webhook/whatsapp`.
11. Send a WhatsApp text message and confirm it appears in conversations.
12. Send a product image and confirm the bot replies with confirmation, choices, or clearer-photo fallback.
13. Create a test order through chat.
14. Send a payment screenshot and confirm order moves to payment review, not auto-approved.
15. Approve/reject from dashboard and confirm status/stock behavior.
